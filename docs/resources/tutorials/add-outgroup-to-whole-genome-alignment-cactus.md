# Adding an outgroup to a whole genome alignment

{{ author_row(page) }}

Once you have your [HAL file with a whole genome alignment](whole-genome-alignment-cactus.md), you may find that you need to add samples to it as your research questions expand. Re-running the whole alignment pipeline may be too computationally expensive. While we provide a workflow to [add genomes to branches of the tree in your HAL file](add-to-whole-genome-alignment-cactus.md), the process for adding an **outgroup** to the alignment is slightly different. We provide the following pipeline to implement those steps.

??? example "The add-outgroup pipeline's rulegraph"

    Here is the rulegraph for the pipeline. This one is fairly straightforward: the new outgroup genome is aligned to the root sequence from the original HAL file, creating a small sub-alignment with a new root. The old alignment is then merged into this one by the old root node.

    <center>
        <img src="https://raw.githubusercontent.com/harvardinformatics/cactus-snakemake/main/tests/evolverMammals/rulegraphs-dags/cactus-add-outgroup-rulegraph.png" alt="A directed cyclic graph showing the rules for the pipeline.">
    </center>

## Getting started

If you've already set up cactus-snakemake with `./cactus_snakemake setup`, for example to make your HAL file with our [whole genome alignment pipeline](whole-genome-alignment-cactus.md), you can [skip ahead](#inputs-you-need-to-prepare). Otherwise, follow the steps below.

## Inputs you need to prepare

To run this pipeline, you will need (corresponding config option given in parentheses):

1. A [**HAL file** :octicons-link-external-24:](https://github.com/ComparativeGenomicsToolkit/Hal){:target="_blank"} with a whole genome alignment generated by Cactus (`input_hal`).
2. The location in the tree to add your alignment (see below).
3. The [**softmasked**](#how-can-i-tell-if-my-genome-fasta-files-are-softmasked) genome [FASTA :octicons-link-external-24:](https://en.wikipedia.org/wiki/FASTA_format){:target="_blank"} file for the genome you want to add to the alignment (`new_genome_fasta`).
4. A reference genome to project the alignment to MAF format (`maf_reference`).

!!! warning "[The FASTA file must be softmasked! :octicons-link-external-24:](https://github.com/ComparativeGenomicsToolkit/cactus/blob/master/doc/progressive.md#interface){:target="_blank"}"

    The genome you provide in FASTA format must be softmasked before running Cactus, otherwise the program will likely not complete. You can tell if a genome FASTA file is masked by the presence of lower-case nucleotides: a, t, c, or g. If your FASTA file has these lower-case characters, it has likely been softmasked. If not, you will have to mask the genome with a tool like [RepeatMasker :octicons-link-external-24:](https://www.repeatmasker.org/){:target="_blank"}. Also importantly, the FASTA files should **not** be **hard** masked, meaning the masked bases are replaced with Ns.

### The location in the tree to add your alignment

Each HAL file requires a phylogenetic tree to generate. When adding a genome to an alignment, we also must add its location in the tree. The easiest way to know this tree and how Cactus has labeled the nodes in it is to run the command:

```bash
halStats --tree example.hal
```

replacing `example.hal` with your HAL's file name. This will print the tree to the screen. For example, in the context of the evolverMammals test data and using the singularity image, we would run the following:

```bash
singularity exec --cleanenv <cactus-image-name>.sif halStats --tree evolverMammals.hal
```

which would result in:

```bash
((simHuman_chr6:0.144018,(simMouse_chr6:0.084509,simRat_chr6:0.091589)mr:0.271974)Anc1:0.020593,(simCow_chr6:0.18908,simDog_chr6:0.16303)Anc2:0.032898)Anc0;
```

Now that we have the tree, we need to figure out where to put our new genome. We will need to come up with the following information:

1. The **label or name** of the root node in the original HAL file (`old_root_name`).
2. A **tip label** or name for our new genome (`new_genome_name`).
3. A **label or name** for the new root node in our tree (`new_root_name`).
4. The **branch length** of the new branch connecting the new genome to the new root (`branch_length_from_new_genome`).
5. The **branch length** of the new branch connecting the old root to the new root (`branch_length_from_old_root`).

We borrow and slightly modify an [image from the cactus documentation :octicons-link-external-24:](https://github.com/ComparativeGenomicsToolkit/cactus/blob/master/doc/updating-alignments.md#adding-a-new-genome){:target="_blank"} to visualize these pieces of information on an example tree:

<center>
    <img src="../../../../img/tutorials/cactus-adding-outgroup.png" alt="Two panels, the first showing a phylogenetic tree with 3 tips and internal nodes labeled, the second showing a 4th tip being added to the tree as an outgroup.">
</center> 

In this context, we are adding the genome with the name **"newGenome"** as an outgroup to our HAL. To do so, we are creating a new root in our tree called **"newRoot"** and connecting it to the original root node, **"5"**. We must supply lengths for the two new branches descending from newRoot.

!!! tip "No branch lengths on Cactus input tree"

    Cactus doesn't strictly require branch lengths on the input tree. In that case, it arbitrarily gives every branch a length of 1. If your input tree to cactus didn't have branch lengths or the output of `halStats --tree` shows only branch lengths of 1.0, then you don't need to specify the new branch lengths. These will automatically be set to 1.0.

#### Original root node

For the name of the original root node, this will usually be called either **Anc0** or **Anc00**. To find out for certain, you can use the tree displayed above from `halStats`.

If you're very good at parsing Newick tree strings by eye, you may be able to see the name of the root node from that text string (here it is **Anc0**). However this is a relatively small tree. In most cases, you'll want to look at an image of the tree. Consider using some sort of tree viewing software like [SeaView :octicons-link-external-24:](https://doua.prabi.fr/software/seaview){:target="_blank"} or [the ape library in R :octicons-link-external-24:](https://cran.r-project.org/web/packages/ape/index.html){:target="_blank"}. EMBL also has an [online, interactive tree viewer :octicons-link-external-24:](https://itol.embl.de/){:target="_blank"} where you can just paste the tree string to see an image of it.

The other 4 pieces of information you'll have to come up with on your own, but once you have all 5 pieces of information from the tree listed above, you're ready to move on to prepare the config file.

### Reference sample

In order to run the last step of the workflow that converts the HAL format to a readable MAF format (See [pipeline outputs](#pipeline-outputs) for more info), you will need to select one assembly as a reference assembly. The reference assembly's coordinate system will be used for projection to MAF format. You should indicate the reference assembly in the config file (outlined below). For instance, if I wanted my reference sample in the above tree to be the genome labeled **1** in the tree, I would put the string `1` in the `maf_reference` line of the config file.

### Preparing the Snakemake config file

Once you have all the information listed above, you can enter it into the config file along with some other information to know where to look for files and write output. Create a starter config file from the pipeline's template with `init`:

```bash
./cactus_snakemake init add-outgroup -o my-config.yaml
```

This copies the pipeline's [config template :octicons-link-external-24:](https://github.com/harvardinformatics/cactus-snakemake/blob/main/config-templates/add-outgroup-config-template.yaml){:target="_blank"} (`config-templates/add-outgroup-config-template.yaml` in your cactus-snakemake folder) to `my-config.yaml`. Without `-o`, it's written to `./add-outgroup-config.yaml`. `init` won't overwrite an existing file unless you add `--force`. Fill in the blank fields before running [prep](#prep).

!!! tip "See an example config file"

    The config for the Cactus test data can be found [here :octicons-link-external-24:](https://github.com/harvardinformatics/cactus-snakemake/blob/main/tests/evolverMammals/evolverMammals-add-outgroup-cfg.yaml){:target="_blank"} or at `tests/evolverMammals/evolverMammals-add-outgroup-cfg.yaml` in your cactus-snakemake folder.

The config file contains 3 sections: one for specifying the input and output options, one for specifying resources for the various rules (see [below](#specifying-resources-for-each-rule)), and one for optional settings that most runs can leave blank. The first part should look something like this:

```
cactus_path: <path/to/cactus-singularity-image OR download OR version tag (e.g. v3.3.0)>

input_hal: <path/to/hal-file>

old_root_name: <label of the root in the input_hal>

new_genome_name: <tip label of new genome>

new_genome_fasta: <path/to/new/genome.fasta>

new_root_name: <label for new root node connected to the new genome and the old root>

branch_length_from_new_genome: <new branch length to connect the new genome to the new root>

branch_length_from_old_root: <new branch length to connect the old root to the new root>

output_dir: <path/to/desired/output-directory>

final_prefix: <desired name of final .hal and .maf files with all genomes appended>

maf_reference: <Genome ID from the HAL file>

maf_include_anc: <True/False>

tmp_dir: <path/to/tmp-dir/>

use_gpu: <True/False>
```

Simply replace the string surrounded by <> with the path or option desired. Below is a table summarizing these options, along with the optional setting at the bottom of the config file:

| Option                          | Description                                                                 |
|-------------------------------- | ----------------------------------------------------------------------------|
| `cactus_path`                   | The Cactus Singularity image to use: a file path, a version tag (e.g. `v3.3.0`), or `download` for the latest release. This is needed whether `use_gpu` is True or False. See the box below the table. |
| `input_hal`                     | Path to the previously generated HAL file to which you want to add a new genome. |
| `old_root_name`                 | The label of the root in the input HAL, can be retrieved with `halStats --tree`. |
| `new_genome_name`               | The label to give your new genome in the tree and HAL file. |
| `new_genome_fasta`              | The path to the FASTA file containing the new genome to add to the alignment. |
| `new_root_name`                 | The name to give the new root node connected to the new genome and the old root. |
| `branch_length_from_new_genome` | The length of the branch to create that will connect your new genome to the new root (default: 1.0). |
| `branch_length_from_old_root`   | The length of the branch to create that will connect the old root to the new root (default: 1.0). |
| `output_dir`                    | Directory where all the output will be written. It will be created if it doesn't exist. |
| `final_prefix`                  | The name of the final .hal and .maf files with all aligned genomes appended. The final files will be `<final_prefix>.hal` and `<final_prefix>.<maf_reference>.maf` (see [Pipeline outputs](#pipeline-outputs)). These files will be placed within `output_dir`. |
| `maf_reference`                 | The label for the genome to use when converting from HAL to MAF. This means that the MAF alignment will be projected on to that genome's coordinate system. |
| `maf_include_anc`               | Whether to include the ancestral genomes in the MAF files (True/False). If `False` (the default), they are left out. |
| `tmp_dir`                       | A temporary directory for Snakemake and Cactus to use. Should have lots of space. |
| `use_gpu`                       | Whether to use the GPU version of Cactus for the alignment (True/False). |
| `singularity_bind_paths`        | **Optional.** A YAML list of extra Singularity bind paths to add to every container command, each in `src[:dest[:opts]]` format, e.g. `/nfs6:/nfs6` or `/scratch:/scratch:rw`. Only needed if some of your files are on a filesystem that isn't available inside the container by default; jobs failing to find files that do exist are the usual sign. Leave blank or set to `[]` to use the cluster defaults only. |

#### Specifying resources for each rule

Below these options in the config file are further options for specifying resource usage for each rule that the pipeline will run, starting with a `default:` entry. For example:

```
rule_resources:
  default:
    partition: shared
    mem_mb: 10000
    cpus: 1
    gpus: 0
    time: 30

  preprocess:
    partition: shared
    mem_mb: 25000
    cpus: 8
    time: 30

  blast:
    partition: gpu    # If use_gpu is True, this must be a partition with GPUs
    mem_mb: 50000
    cpus: 48
    gpus: 1           # Set gpus or gres, not both. Both are ignored if use_gpu is False
    time: 30
```

**The rule _blast_ is the only one that uses GPUs if `use_gpu` is True.**

You will have to determine the proper resource usage for your dataset. Generally, the larger the genomes, the more time and memory each job will need, and the more you will benefit from providing more CPUs and GPUs.

We have an [example of resource allocation and usage for creation of a new HAL file](whole-genome-alignment-cactus.md#example-resource-usage-on-a-dataset-of-22-turtle-genomes). Since updating a HAL file uses the same steps, just with fewer rounds, you can gauge resource usage with this example.

## Running the pipeline

With [everything installed](#getting-started) and the [config file](#preparing-the-snakemake-config-file) set up, you are now ready to run the pipeline. This takes three steps: prep, a dry-run, and then the real run.

### Prep

Prep is run once for each output directory, before the pipeline itself:

```bash
./cactus_snakemake prep add-outgroup --configfile my-config.yaml
```

For this pipeline, prep only resolves the Cactus image, downloading it if `cactus_path` is `download` or a version tag. There is no prepare command for adding an outgroup.

<!-- Shared text: docs/assets/snippets/cactus-snakemake/prep.md -->

--8<-- "docs/assets/snippets/cactus-snakemake/prep.md"

### Do a `--dryrun` first

Next, we want to make sure everything is set up properly by using the `--dryrun` option. This tells Snakemake to display what jobs it is going to run without actually submitting them. This is important to do before actually submitting the jobs so we can catch any setup errors beforehand.

```bash
./cactus_snakemake run add-outgroup --configfile my-config.yaml -j 20 -e slurm --dryrun
```

<!-- Shared text: docs/assets/snippets/cactus-snakemake/run-command.md -->

--8<-- "docs/assets/snippets/cactus-snakemake/run-command.md"

If this completes successfully, you should see a bunch of blue, yellow, and green text on the screen, ending with a summary of the jobs to be run. For the repo's [test dataset](#test-dataset), which adds the simulated gorilla genome as an outgroup above the old root `Anc0`, under a new root named `newRoot`, it looks like this:

```
Job stats:
job                 count
----------------  -------
get_root_fasta          1
make_input_files        1
preprocess              1
blast                   1
align                   1
combine_hals            1
maf                     1
all                     1
total                   8
```

The order of the rows can differ between Snakemake versions.

The `make_input_files` job writes the pipeline's two input files. Like `all`, it's a local job: it runs inside the main Snakemake process on the node where you start the run, is never submitted to the cluster, and requests no resources, so it has no entry in `rule_resources`.

If you see any red text, that likely means an error has occurred that must be addressed before you run the pipeline.

### Submitting the jobs

If you're satisfied that the `--dryrun` has completed successfully and you are ready to start submitting Cactus jobs to the cluster, you can do so by simply removing the `--dryrun` option from the command above:

```bash
./cactus_snakemake run add-outgroup --configfile my-config.yaml -j 20 -e slurm
```

This will start submitting jobs to SLURM. On your screen, you will see continuous updates regarding job status in blue text. In another terminal, you can also check on the status of your jobs by running `squeue -u <your user id>`. 

<!-- Shared text: docs/assets/snippets/cactus-snakemake/keep-running.md -->

--8<-- "docs/assets/snippets/cactus-snakemake/keep-running.md"

Depending on the number of genomes, their sizes, and your wait in the queue, you will hopefully have your updated whole genome alignment within a few hours!

### Test dataset

Cactus provides a test dataset which we have set up to run in the `tests/evolverMammals/` folder of the cactus-snakemake repo. 

Here is a breakdown of the files so you can investigate them and prepare similar ones for your project:

| File/directory                         | Description |
| -------------------------------------- | ----------- |
| `evolverMammals-seq/`                  | This directory contains the input sequence files for the test dataset in FASTA format. |
| `evolverMammals-add-outgroup-cfg.yaml` | This is the config file for this pipeline and has all of the options you would need to set up for your own project. |

You will first need to [run the align test](whole-genome-alignment-cactus.md#test-dataset) to generate the HAL file, `evolverMammals-align-out/evolverMammals.hal`, which this test starts from. This pipeline then adds the simulated gorilla genome to it as an outgroup above the old root, `Anc0`, under a new root named `newRoot`. We recommend running this test dataset before setting up your own project.

The config file doesn't need any edits: it downloads the latest Cactus image, uses its own temporary directory inside `tests/evolverMammals/`, and leaves the partitions blank. Its output is written to `tests/evolverMammals/evolverMammals-add-outgroup-out/`.

The paths in the config file are relative to the dataset's folder, so the test is run from there. Change into `tests/evolverMammals/`, then run prep and a dry-run:

```bash
cd tests/evolverMammals/
../../cactus_snakemake prep add-outgroup --configfile evolverMammals-add-outgroup-cfg.yaml
../../cactus_snakemake run add-outgroup --configfile evolverMammals-add-outgroup-cfg.yaml -j 20 -e slurm --dryrun
```

Prep downloads the Cactus image once, into `tests/evolverMammals/`. If the dry-run completes without error, run the pipeline by removing the `--dryrun` option:

```bash
../../cactus_snakemake run add-outgroup --configfile evolverMammals-add-outgroup-cfg.yaml -j 20 -e slurm
```

Since the partitions are blank, you can optionally add `--slurm-partition-config <path>` to these commands to have partitions selected automatically.

## Pipeline outputs

The pipeline will output a [.fa :octicons-link-external-24:](https://en.wikipedia.org/wiki/FASTA_format){:target="_blank"} file for the old root node, a [.paf :octicons-link-external-24:](https://github.com/lh3/miniasm/blob/master/PAF.md){:target="_blank"} for the new root node, and a [.hal :octicons-link-external-24:](https://github.com/ComparativeGenomicsToolkit/hal/blob/master/README.md){:target="_blank"} that includes the original HAL alignment along with the added genome and new root node. The final alignment file will be `<final_prefix>.hal`, where `<final_prefix>` is whatever you specified in the config file.

!!! warning "The original HAL file will essentially be copied"

    In order to add the new genome as an outgroup, the old HAL file is appended to the new one, leaving the old HAL file in place. While this preserves the old HAL file, it does create a copy of a potentially large file. Be aware of your data storage capacity as you run this pipeline.

The final alignment will also be presented in MAF format as `<final_prefix>.<maf_reference>.maf`, again where `<maf_reference>` is whatever you set in the config file. This file will include duplicate sequences. Another MAF file, `<final_prefix>.<maf_reference>.nodupes.maf` will also be generated, which is the alignment in MAF format with no duplicate sequences. The de-duplicated MAF file is generated with `--dupeMode single`. By default (`maf_include_anc: False`), the ancestral genomes are left out of the MAF files (`cactus-hal2maf --noAncestors`). Set `maf_include_anc: True` to include them. See the [Cactus documentation regarding MAF export :octicons-link-external-24:](https://github.com/ComparativeGenomicsToolkit/cactus/blob/master/doc/progressive.md#maf-export){:target="_blank"} for more info.

Prep also writes `<output_dir>/prep-manifest.yaml`, its record of what it did. The `<output_dir>/logs/` folder holds a `<genome>.preprocess.seqfile.txt` for each preprocess job: the copy of the input file given to `cactus-preprocess`, kept for reference.

A suite of tools called [HAL tools :octicons-link-external-24:](https://github.com/ComparativeGenomicsToolkit/Hal){:target="_blank"} is included with the Cactus singularity image if you need to manipulate or analyze .hal files. There are many tools for manipulating MAF files, though they are not always easy to use. The makers of Cactus also develop [taffy :octicons-link-external-24:](https://github.com/ComparativeGenomicsToolkit/taffy){:target="_blank"}, which can manipulate MAF files by converting them to TAF files.
