# Replacing a genome in a whole genome alignment

{{ author_row(page) }}

Once you have your [HAL file with a whole genome alignment](whole-genome-alignment-cactus.md), a common occurrence may be the release of a new version of one of the genomes in it. For this reason, and for others, the developers of Cactus provide a method to  [replace a genome in a HAL file :octicons-link-external-24:](https://github.com/ComparativeGenomicsToolkit/cactus/blob/master/doc/cactus-update-prepare.md#replacing-a-genome){:target="_blank"}. Here, we replicate this method as a Snakemake pipeline by emulating the steps laid out by [`cactus-update-prepare` :octicons-link-external-24:](https://github.com/ComparativeGenomicsToolkit/cactus/blob/master/doc/cactus-update-prepare.md){:target="_blank"}.

??? example "The replace-genome pipeline's rulegraph"

    Here is the rulegraph for the pipeline. It performs one round of alignment: the old genome is removed from the HAL, and the parent of the replaced genome is re-aligned with the new genome.

## Getting started

If you've already set up cactus-snakemake with `./cactus_snakemake setup`, for example to make your HAL file with our [whole genome alignment pipeline](whole-genome-alignment-cactus.md), you can [skip ahead](#inputs-you-need-to-prepare). Otherwise, follow the steps below.

??? warning "Upgrading a replace-genome run from v3"

    * For an output directory from v3, prep rewrites `seq_file.in` and `seq_file.out` one last time, so the next run redoes this pipeline's steps from `preprocess` once, as every v3 resume did.
    * If a run with `overwrite_original_hal: True` has already started modifying the input HAL, don't prep it again. Start over from a copy of the original HAL.

With that, you should be ready to set-up your data for the pipeline!

## Inputs you need to prepare

To run this pipeline, you will need (corresponding config option given in parentheses):

1. A [**HAL file** :octicons-link-external-24:](https://github.com/ComparativeGenomicsToolkit/Hal){:target="_blank"} with a whole genome alignment generated by Cactus (`input_hal`).
2. The **name** of the genome you want to replace in the HAL file (`replace`).
3. The **name** the replacement genome will have in the HAL file (`new_genome_name`).
4. The [**softmasked**](#how-can-i-tell-if-my-genome-fasta-files-are-softmasked) genome [FASTA :octicons-link-external-24:](https://en.wikipedia.org/wiki/FASTA_format){:target="_blank"} file for the genome you want to add to the alignment (`new_genome_fasta`).
5. A reference genome to project the alignment to MAF format (`maf_reference`).

!!! warning "[The FASTA file must be softmasked!](https://github.com/ComparativeGenomicsToolkit/cactus/blob/master/doc/progressive.md#interface)"

    The genome you provide in FASTA format must be softmasked before running Cactus, otherwise the program will likely not complete. You can tell if a genome FASTA file is masked by the presence of lower-case nucleotides: a, t, c, or g. If your FASTA file has these lower-case characters, it has likely been softmasked. If not, you will have to mask the genome with a tool like [RepeatMasker :octicons-link-external-24:](https://www.repeatmasker.org/){:target="_blank"}. Also importantly, the FASTA files should **not** be **hard** masked, meaning the masked bases are replaced with Ns.

### The name of the genome to replace

If you need to look up the labels used in the HAL file, `halStats` has several methods. One is the `--tree` command, which prints out the phylogenetic tree used to generate the alignment:

```bash
halStats --tree example.hal
```

Replace `example.hal` with your HAL's file name. This will print the tree to the screen and you can look up the names of the genomes there as they are the tip labels in the tree. For example, in the context of the evolverMammals test data and using the singularity image, we would run the following:

```bash
singularity exec --cleanenv <cactus-image-name>.sif halStats --tree evolverMammals.hal
```

which would result in:

```bash
((simHuman_chr6:0.144018,(simMouse_chr6:0.084509,simRat_chr6:0.091589)mr:0.271974)Anc1:0.020593,(simCow_chr6:0.18908,simDog_chr6:0.16303)Anc2:0.032898)Anc0;
```

If we want to replace the *simHuman_chr6* genome in our HAL with a new version of the sequence, we would set this label as the value for `replace` in our config file below.

You can also run `halStats --genomes example.hal` to print out the labels without the Newick tree formatting.

### The name of the new genome

You'll also choose the name the replacement genome will have in the HAL file (`new_genome_name`). It can be the same as the genome being replaced (set in `replace`) or a new name. Cactus v3.0.0 and later allow either.

### Reference sample

In order to run the last step of the workflow that converts the HAL format to a readable MAF format (See [pipeline outputs](#pipeline-outputs) for more info), you will need to select one assembly as a reference assembly. The reference assembly's coordinate system will be used for projection to MAF format. You should indicate the reference assembly in the config file (outlined below). For instance, if I wanted my reference sample in the above tree to be the genome labeled **simHuman_chr6** in the tree, I would put the string `simHuman_chr6` in the `maf_reference:` line of the config file.

### Preparing the Snakemake config file

??? info "The Cactus replace input file"

    The various Cactus commands depend on a single input file with information about the genomes to align. For this pipeline, prep writes this file for you at `[output_dir]/cactus-replace-input.txt`. This file is a simple tab delimited file and should contain one line:

    ```
    [tip label to add to tree]   [path/to/genome/fasta.file]
    ```

    For more information about the Cactus update input file, see their [official documentation :octicons-link-external-24:](https://github.com/ComparativeGenomicsToolkit/cactus/blob/master/doc/cactus-update-prepare.md#adding-genomes-examples){:target="_blank"}.

Once you have all the information listed above, you can enter it into the config file along with some other information to know where to look for files and write output. Create a starter config file from the pipeline's template with `init`:

```bash
./cactus_snakemake init replace-genome -o my-config.yaml
```

This copies the pipeline's [config template :octicons-link-external-24:](https://github.com/harvardinformatics/cactus-snakemake/blob/main/config-templates/replace-genome-config-template.yaml){:target="_blank"} (`config-templates/replace-genome-config-template.yaml` in your cactus-snakemake folder) to `my-config.yaml`. Without `-o`, it's written to `./replace-genome-config.yaml`. `init` won't overwrite an existing file unless you add `--force`. Fill in the blank fields before running [prep](#prep).

!!! tip "See an example config file"

    The config for the Cactus test data can be found [here :octicons-link-external-24:](https://github.com/harvardinformatics/cactus-snakemake/blob/main/tests/evolverMammals/evolverMammals-replace-genome-cfg.yaml){:target="_blank"} or at `tests/evolverMammals/evolverMammals-replace-genome-cfg.yaml` in your cactus-snakemake folder.

The config file contains 3 sections: one for specifying the input and output options, one for specifying resources for the various rules (see [below](#specifying-resources-for-each-rule)), and one for optional settings that most runs can leave blank. The first part should look something like this:

```
cactus_path: <path/to/cactus-singularity-image OR download OR version tag (e.g. v3.3.0)>

input_hal: <path/to/hal-file>

replace: <tip label of genome to replace>

new_genome_fasta: <path/to/new/genome.fasta>

new_genome_name: <tip label the new genome will have in the HAL file>

output_dir: <path/to/desired/output-directory>

overwrite_original_hal: <True/False>

final_prefix: <desired name of final .hal and .maf files with all genomes appended>

maf_reference: <Genome ID from the HAL file>

maf_include_anc: <True/False>

tmp_dir: <path/to/tmp-dir/>

use_gpu: <True/False>
```

Simply replace the string surrounded by <> with the path or option desired. Below is a table summarizing these options, along with the optional setting at the bottom of the config file:

| Option                   | Description                                                                 |
|------------------------- | ----------------------------------------------------------------------------|
| `cactus_path`            | The Cactus Singularity image to use: a file path, a version tag (e.g. `v3.3.0`), or `download` for the latest release. This is needed whether `use_gpu` is True or False. See the box below the table. |
| `input_hal`              | Path to the previously generated HAL file in which you want to replace a genome. |
| `replace`                | The label of the genome to replace in the HAL file. |
| `new_genome_fasta`       | The path to the FASTA file containing the new genome to add to the alignment. |
| `new_genome_name`        | The name the replacement genome will have in the HAL file. It can be the same as the genome being replaced (set in `replace`) or a new name; Cactus v3.0.0 and later allow either. |
| `output_dir`             | Directory where all the output will be written. It will be created if it doesn't exist. |
| `overwrite_original_hal` | Whether to overwrite the original HAL file (`True`) or to make a copy and add the new genome to it (`False`). Overwriting will save storage space, but risks corruption of the original file. |
| `final_prefix`           | The name of the final .hal (if `overwrite_original_hal` is `False`) and .maf files with all aligned genomes appended. The final files will be `<final_prefix>.hal` and `<final_prefix>.<maf_reference>.maf` (see [Pipeline outputs](#pipeline-outputs)). These files will be placed within `output_dir`. |
| `maf_reference`          | The label for the genome to use when converting from HAL to MAF. This means that the MAF alignment will be projected on to that genome's coordinate system. |
| `maf_include_anc`        | Whether to include the ancestral genomes in the MAF files (True/False). If `False` (the default), they are left out. |
| `tmp_dir`                | A temporary directory for Snakemake and Cactus to use. Should have lots of space. |
| `use_gpu`                | Whether to use the GPU version of Cactus for the alignment (True/False). |
| `singularity_bind_paths` | **Optional.** A YAML list of extra Singularity bind paths to add to every container command, each in `src[:dest[:opts]]` format, e.g. `/nfs6:/nfs6` or `/scratch:/scratch:rw`. Only needed if some of your files are on a filesystem that isn't available inside the container by default; jobs failing to find files that do exist are the usual sign. Leave blank or set to `[]` to use the cluster defaults only. |

#### Specifying resources for each rule

Below these options in the config file are further options for specifying resource usage for each rule that the pipeline will run, starting with a `default:` entry. For example:

```
rule_resources:
  default:
    partition: shared
    mem_mb: 10000
    cpus: 1
    gpus: 0
    time: 30

  preprocess:
    partition: shared
    mem_mb: 25000
    cpus: 8
    time: 30

  blast:
    partition: gpu    # If use_gpu is True, this must be a partition with GPUs
    mem_mb: 50000
    cpus: 48
    gpus: 1           # Set gpus or gres, not both. Both are ignored if use_gpu is False
    time: 30
```

**The rule _blast_ is the only one that uses GPUs if `use_gpu` is True.**

You will have to determine the proper resource usage for your dataset. Generally, the larger the genomes, the more time and memory each job will need, and the more you will benefit from providing more CPUs and GPUs.

We have an [example of resource allocation and usage for creation of a new HAL file](whole-genome-alignment-cactus.md#example-resource-usage-on-a-dataset-of-22-turtle-genomes). Since updating a HAL file uses the same steps, just with fewer rounds, you can gauge resource usage with this example.

## Running the pipeline

With [everything installed](#getting-started) and the [config file](#preparing-the-snakemake-config-file) set up, you are now ready to run the pipeline. This takes three steps: prep, a dry-run, and then the real run.

### Prep

Prep is run once for each output directory, before the pipeline itself:

```bash
./cactus_snakemake prep replace-genome --configfile my-config.yaml
```

For this pipeline, prep resolves the Cactus image (downloading it if `cactus_path` is `download` or a version tag), writes the [Cactus replace input file](#preparing-the-snakemake-config-file), and runs `cactus-update-prepare`, which also extracts sequences from the input HAL. For large alignments this can take a while, and it runs on whatever node you run prep from, so consider running prep in an interactive job rather than on a login node. Its log is written to `<output_dir>/logs/cactus-update-prepare.log`.

<!-- Shared text: docs/assets/snippets/cactus-snakemake/prep.md -->

--8<-- "docs/assets/snippets/cactus-snakemake/prep.md"

### Do a `--dryrun` first

Next, we want to make sure everything is set up properly by using the `--dryrun` option. This tells Snakemake to display what jobs it is going to run without actually submitting them. This is important to do before actually submitting the jobs so we can catch any setup errors beforehand.

```bash
./cactus_snakemake run replace-genome --configfile my-config.yaml -j 20 -e slurm --dryrun
```

<!-- Shared text: docs/assets/snippets/cactus-snakemake/run-command.md -->

--8<-- "docs/assets/snippets/cactus-snakemake/run-command.md"

If this completes successfully, you should see a bunch of blue, yellow, and green text on the screen, ending with a summary of the jobs to be run. For the repo's [test dataset](#test-dataset), which replaces `simHuman_chr6` with `simGorilla_chr6`, it looks like this:

```
Job stats:
job                count
---------------  -------
copy_or_get_hal        1
preprocess             1
blast                  1
remove_genome          1
align                  1
replace_genome         1
maf                    1
all                    1
total                  8
```

The order of the rows can differ between Snakemake versions.

If you see any red text, that likely means an error has occurred that must be addressed before you run the pipeline.

### Submitting the jobs

If you're satisfied that the `--dryrun` has completed successfully and you are ready to start submitting Cactus jobs to the cluster, you can do so by simply removing the `--dryrun` option from the command above:

```bash
./cactus_snakemake run replace-genome --configfile my-config.yaml -j 20 -e slurm
```

This will start submitting jobs to SLURM. On your screen, you will see continuous updates regarding job status in blue text. In another terminal, you can also check on the status of your jobs by running `squeue -u <your user id>`. 

<!-- Shared text: docs/assets/snippets/cactus-snakemake/keep-running.md -->

--8<-- "docs/assets/snippets/cactus-snakemake/keep-running.md"

Depending on the number of genomes, their sizes, and your wait in the queue, you will hopefully have your updated whole genome alignment within a few hours!

### Test dataset

Cactus provides a test dataset which we have set up to run in the `tests/evolverMammals/` folder of the cactus-snakemake repo. 

Here is a breakdown of the files so you can investigate them and prepare similar ones for your project:

| File/directory                           | Description |
| ---------------------------------------- | ----------- |
| `evolverMammals-seq/`                    | This directory contains the input sequence files for the test dataset in FASTA format. |
| `evolverMammals-replace-genome-cfg.yaml` | This is the config file for this pipeline and has all of the options you would need to set up for your own project. |

You will first need to [run the align test](whole-genome-alignment-cactus.md#test-dataset) to generate the HAL file, `evolverMammals-align-out/evolverMammals.hal`, which this test starts from. This pipeline then replaces the `simHuman_chr6` genome in it with the simulated gorilla genome, named `simGorilla_chr6`. We recommend running this test dataset before setting up your own project.

The config file doesn't need any edits: it downloads the latest Cactus image, uses its own temporary directory inside `tests/evolverMammals/`, and leaves the partitions blank. Its output is written to `tests/evolverMammals/evolverMammals-replace-genome-out/`.

The paths in the config file are relative to the dataset's folder, so the test is run from there. Change into `tests/evolverMammals/`, then run prep and a dry-run:

```bash
cd tests/evolverMammals/
../../cactus_snakemake prep replace-genome --configfile evolverMammals-replace-genome-cfg.yaml
../../cactus_snakemake run replace-genome --configfile evolverMammals-replace-genome-cfg.yaml -j 20 -e slurm --dryrun
```

Prep downloads the Cactus image once, into `tests/evolverMammals/`. If the dry-run completes without error, run the pipeline by removing the `--dryrun` option:

```bash
../../cactus_snakemake run replace-genome --configfile evolverMammals-replace-genome-cfg.yaml -j 20 -e slurm
```

Since the partitions are blank, you can optionally add `--slurm-partition-config <path>` to these commands to have partitions selected automatically.

## Pipeline outputs

The pipeline will output a NEW [.paf :octicons-link-external-24:](https://github.com/lh3/miniasm/blob/master/PAF.md){:target="_blank"} and [.hal :octicons-link-external-24:](https://github.com/ComparativeGenomicsToolkit/hal/blob/master/README.md){:target="_blank"} file for the ancestral node of the genome you are replacing. It will also generate a [.fa :octicons-link-external-24:](https://en.wikipedia.org/wiki/FASTA_format){:target="_blank"} file of the new genome sequence, masked by Cactus. 

If you specified `overwrite_original_hal: False`, the final alignment file containing all sequences and the NEW sequence in place of the old one will be `<final_prefix>.hal`, where `<final_prefix>` is whatever you specified in the config file. Otherwise, the original HAL will be modified in place.

The final alignment will also be presented in MAF format as `<final_prefix>.<maf_reference>.maf`, again where `<maf_reference>` is whatever you set in the config file. This file will include duplicate sequences. Another MAF file, `<final_prefix>.<maf_reference>.nodupes.maf` will also be generated, which is the alignment in MAF format with no duplicate sequences. The de-duplicated MAF file is generated with `--dupeMode single`. By default (`maf_include_anc: False`), the ancestral genomes are left out of the MAF files (`cactus-hal2maf --noAncestors`). Set `maf_include_anc: True` to include them. See the [Cactus documentation regarding MAF export :octicons-link-external-24:](https://github.com/ComparativeGenomicsToolkit/cactus/blob/master/doc/progressive.md#maf-export){:target="_blank"} for more info.

Prep also writes `<output_dir>/prep-manifest.yaml`, its record of what it did. The `<output_dir>/logs/` folder holds `cactus-update-prepare.log` and, for each preprocess job, a `<genome>.preprocess.seqfile.txt`: the copy of the input file given to `cactus-preprocess`, kept for reference.

A suite of tools called [HAL tools :octicons-link-external-24:](https://github.com/ComparativeGenomicsToolkit/Hal){:target="_blank"} is included with the Cactus singularity image if you need to manipulate or analyze .hal files. There are many tools for manipulating MAF files, though they are not always easy to use. The makers of Cactus also develop [taffy :octicons-link-external-24:](https://github.com/ComparativeGenomicsToolkit/taffy){:target="_blank"}, which can manipulate MAF files by converting them to TAF files.
